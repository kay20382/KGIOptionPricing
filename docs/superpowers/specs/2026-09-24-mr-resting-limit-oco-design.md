# MR 實盤限價括號單與停損 OCO 協調設計

日期：2026-09-24

## 1. 目標

讓 `MeanReversionScalper` 在實盤中將已計算且固定於本輪週期的進場價與停利價送成交易所限價單，讓委託能在市場排隊；固定停損仍由本機行情條件觸發，觸發後才以市價單平倉。進場、停利、停損和晚到回報都必須依策略實例與週期精確關聯，且不得因撤單競態造成重複平倉或誤反手。

本設計只改變 MR 的實盤委託執行方式，不修改訊號、價位公式、`F`／`K`／`H` 等參數預設值、每筆一口風控、商品白名單或費用計算。模擬與歷史重播使用相同角色與委託生命週期，但不連接券商。

## 2. 範圍與非目標

範圍：

- MR 的兩側進場使用券商限價單；工作中的買價／賣價取自同一括號週期已凍結的價格。
- MR 的停利使用券商限價單，價位沿用該週期既有的反向出場價。
- MR 的固定停損保留本機 stop trigger；觸發後依 OCO 協調完成限價撤單與成交結算，再送市價停損單。
- 共用實盤執行／路由層按 `StrategyInstanceId + StrategyRunGeneration + CycleId` 協調相同週期的進場 OCO 與出場 OCO。操作只限該組明確識別的委託。
- 持久化 OCO 階段及待辦動作，供既有重啟回補架構恢復或隔離。

非目標：

- 不假設或依賴券商支援原生 OCO；實作以共用路由器協調的本機 OCO 為準。
- 不改 Wavelet、Nikkei Alpha、Mini Lead、Order Book Trend、PQC 或其他策略的委託意圖。
- 不新增動態追價／改價、滑價模型、委託重掛政策或新的策略訊號。
- 不因模擬測試連接或送出真實券商委託。

## 3. 現況與設計決策

`MeanReversionScalperStrategy.PlaceEntryBracket` 在新週期開始時以當時的中間價與 `_bracketRange` 計算 `_buyEntry`、`_sellEntry`、`_longStop`、`_shortStop`；這些數值在該週期內固定。策略目前將進場與停利以 `PaperOrderType.Limit` 發出。實盤執行器把 `Limit` 當成本機條件，穿價後送市價單；只有 `BrokerLimit` 會映射至券商限價委託。`Stop` 則是本機觸發條件，觸發時目前會先清除本機條件，再直接送市價單。

停利若改為券商限價單，便與本機停損條件分屬兩種訂單集合，原本的本機 OCO 清除方式無法撤掉真實停利委託。故採用共用實盤路由／執行協調器處理 OCO 與事件序列，不在每個策略複製一套非同步撤單競態處理。券商回報仍透過既有 immutable ownership、client/broker alias、成交去重與策略虛擬帳本處理。

## 4. 委託與角色語意

### 4.1 進場括號

MR 在可進場且尚無有效週期時，同時發出：

- `EntryLong`：買進 `BrokerLimit`，價格為當週期 `_buyEntry`。
- `EntryShort`：賣出 `BrokerLimit`，價格為當週期 `_sellEntry`。

兩單必須具有相同策略實例、執行世代與 `CycleId`，並各自持有唯一 `ClientOrderId`。送出後價格不得因後續 rolling range 或中間價更新而移動。

其中一筆首次成交後，立即對另一筆進場單提出精確撤單，並立即為已成交的實際數量建立本機固定停損條件；不得等對側撤單完成才開始保護既有部位。待對側進場單終結且最終成交量水位已對平後，才建立停利限價單。撤單尚未終結時維持週期受控狀態，不得建立下一個進場週期。

若另一側在撤單生效前亦成交，所有實際成交仍須依原 client/broker alias 正常且冪等地入帳。不得忽略或猜測歸屬，也不得再盲目建立一套新的停利／停損括號。協調器須停止該週期的一般新單、重算該策略未平部位；在持倉與工作單狀態明確前保持 `Suspended`／`ReconciliationRequired`。不支援券商原子 OCO 時，系統不可宣稱可消除交易所端的撤單競態。

### 4.2 持倉保護

首次進場成交時，先按已確認的策略淨部位啟用本機停損保護；完成對側進場單撤單／成交結算後，再依實際剩餘策略部位建立停利限價單並確認停損條件仍匹配該淨部位：

- `TakeProfit`：反向 `BrokerLimit`，價位為原週期對應的凍結停利價；不得按最新價格重算。
- `StopLoss`：保留本機 `Stop` 觸發條件；觸發門檻為原週期凍結的 `_longStop` 或 `_shortStop`。該條件不是送到交易所的 stop order。

只有固定停損觸發後的平倉請求使用市價；其角色必須保留為 `StopLoss`，而非一般 `Flatten`。停利成交後，精確取消本機停損條件並完成該週期。

### 4.3 停損 OCO 流程

停損條件被有效行情穿越後，共用協調器必須以單一序列化狀態轉換執行：

1. 將該週期標記為 `StopPending`，抑制同週期重複 stop trigger 與一般新單。
2. 精確撤銷該週期所有仍可能減少／改變該策略持倉的停利限價單；保留 ownership 與成交 tombstone。
3. 等候撤單終態，並等券商終態的最終累積成交量水位與已交付至策略帳本的成交量一致。`CancelPending`、取消失敗、送單結果不明、券商未提供可用終態累積量，或仍有未結算成交時，不可送停損市價單。只有「終態已確認且成交水位已對平」才算撤單／成交結算完成；單有 `Cancelled` 事件不足以放行。
4. 使用策略虛擬帳本已確認的剩餘部位決定反向平倉方向與數量。剩餘部位為零時，不送停損單並將該週期按實際成交結果結束。
5. 剩餘部位非零時，對該剩餘數量只送一次市價 `StopLoss` 委託。市價單拒絕、結果不明或成交量異常時，維持暫停／隔離與原 ownership，禁止自動重送。
6. 完成平倉或進入人工處理後，依共用帳本與策略狀態完成週期收尾；只有部位為零且所有該週期委託終結後才允許新週期。

如果停利在撤單途中已全數成交，步驟 4 必須觀察到零剩餘部位，不送市價單。如果停利部分成交，停損市價單最多平掉尚未平倉的剩餘數量。撤單失敗或無法確認所有回報時，不得假設停利單已不存在。

## 5. 事件排序、冪等與隔離

- 進場／停利／停損／撤單生命週期都使用既有 `StrategyInstanceId + StrategyRunGeneration + ClientOrderId + CycleId + Role`；OCO 關聯不可只依商品、價格或時間建立。
- 同一策略週期的行情觸發、券商委託狀態與成交須由共用執行層序列化；重複事件不得重複提出 cancel 或 stop market。
- 成交先進入共用策略帳本，再處理相關終態及 OCO 後續動作；以 `ExecId` 或既有累積成交水位去重。
- `Cancelled` 生命週期不能抹除可能晚到的成交映射。若券商終態累積成交水位與已交付執行量不一致，OCO 保持等待結算／隔離，不可送可能超量平倉的市價單。若券商不提供終態累積水位，不能以逾時或本機推測替代；需人工核對。
- 在撤單確認、成交結算、保護單拒絕或市價單結果不明期間，狀態須清楚顯示 `StopPending`、`ReconciliationRequired` 或 `Quarantined` 與具體原因；不得顯示已平倉。
- 所有動作只針對 OCO key 所屬策略實例與週期，不影響同商品其他策略。

## 6. 重啟回補

OCO phase、觸發停損的 client order、出場限價單識別、已提出的精確撤單，以及是否已建立唯一 stop-market intent，必須納入共用 ownership journal/checkpoint。重啟時禁止自動續送或重送停損市價單。系統先回補工作委託、成交和帳戶／策略部位，再將週期還原至 `RecoveredPaused`；只有能唯一還原所有 OCO 成員、成交水位與剩餘策略部位時才可由使用者恢復。

若目前券商 API 缺少必要的執行回補資料、同一週期 OCO 成員不完整、stop-market 送單結果不明或策略／帳戶部位不一致，轉為 `Quarantined`／`ReconciliationRequired`，封鎖該商品的一般新單並要求人工對帳。不得以已保存 checkpoint 代替券商真實狀態。

## 7. 模擬與重播

- 策略進場與停利 intent 使用 `BrokerLimit` 語意；模擬 adapter 將其視為限價單，沿用嚴格穿價成交、成交價固定為委託價及現行費用處理，不連線券商。
- 本機 `Stop` 維持由成交行情觸發。模擬 OCO 必須先終結停利委託並結算同一行情批次的所有成交，再按剩餘部位產生一次 stop-market `ExecutionEvent`，避免一根行情同時穿越停利與停損而雙重平倉。
- 歷史重播需用相同事件序列規則；行情與券商回報順序不足以判定先後時，記錄為不確定／保守拒絕，不選擇有利成交。
- 保持每筆一口 live risk gate；若內部模型支援部分成交，所有出口數量以當前策略虛擬淨部位為上限。

## 8. 可觀測性與 UI

沿用共用 order lifecycle、execution 與 strategy observation 記錄，不新增策略專屬記錄器。至少可檢查：OCO key、進場／停利／停損 client id、broker id、限價、撤單請求與終態、觸發行情序號、成交水位、當前策略剩餘部位、stop-market 是否已提交、恢復／隔離原因。

MR 策略狀態／模擬紀錄須區分「限價送出／券商工作中」、「對側進場撤單中」、「停損觸發／等待停利撤單」、「市價停損送出」、「等待人工對帳」及「完成平倉」，不得將未確認的撤單顯示成取消完成。

## 9. 驗收測試

所有測試使用 fake gateway 或 paper execution adapter；不得送出真實委託。

1. MR 開始週期後有兩張真實 BrokerLimit 進場單，價格等於當輪凍結價；後續行情變化不改價。
2. 一側進場成交後只精確撤另一側同週期進場單；其他週期／其他策略訂單不受影響。
3. 一側成交後立即建立本機停損保護並撤銷對側；對側在撤單終態前晚到成交時兩筆均只入帳一次，阻止重複建立括號並進入持倉重新協調／暫停。
4. 進場撤單結算完成後，MR 的停利是 BrokerLimit，停損是本機 Stop trigger；模擬與實盤 request role、價格與數量一致。
5. 停損觸發先發出停利撤單；未收到終態及最終累積成交水位前沒有 stop-market；收到終態且券商最終累積量等於已入帳成交量後，對剩餘部位只送一張 StopLoss 市價單。
6. 停利在撤單途中全數成交時，不送市價停損；部分成交時只按剩餘策略部位市價平倉。
7. 撤單失敗、撤單逾時、未知成交、重複 stop trigger、stop-market 拒單及送單結果不明皆不重送，策略／商品顯示可辨識的暫停或隔離狀態。
8. 撤單確認後晚到成交若與券商最終累積量水位不一致，維持等待／隔離且不送超量 stop market；別名映射仍回到原策略及週期。
9. 重啟時不自動送 stop market；OCO checkpoint 與券商回補一致後為 `RecoveredPaused`，不一致或資料不足為 `Quarantined`。
10. 執行 MR、OrderManagement、StrategyFramework、LiveStrategyRecovery smoke suites 與 Release solution build；既有失敗須區分記錄，不得隱藏或宣稱全綠。

## 10. 完成定義與限制

完成必須證明真實 BrokerLimit mapping、策略週期 OCO 隔離、撤單確認後才停損市價、撤單期間成交／部分成交不會造成超量平倉、stop intent 冪等、checkpoint/recovery fail-closed，以及既有多策略 ownership 與帳本回歸通過。模擬 gateway 測試不證明實際券商端排隊或回報時序；上線前仍須於明確授權的受控市場時段確認 KGI broker 對限價接受、撤單終態及成交累積量回報的行為。
