# 多策略實盤回報路由與重啟回補設計

## 目標與範圍

KGIOptionPricing 的實盤策略必須允許多個策略同時交易同一商品與帳戶，並且使每個策略能準確取得自己的委託、成交、取消、拒單、改單及晚到券商回報。

本設計適用於既有 `StrategyFramework`、`LiveStrategyService`、`KgiLiveStrategyExecutionService` 與 `OrderManager`。它不改變策略訊號、選股、進出場參數或商品規格；策略層持倉及損益仍使用共用帳本，不新增平行策略引擎。

成功條件：

1. 同一帳戶可同時執行多個 225MC 策略，包含相反方向。
2. 任何券商回報皆可依持久化識別碼回到唯一策略實例，不能依商品、帳戶淨部位或時間猜測歸屬。
3. 每個策略可獨立關閉、撤單及平倉，且不影響其他策略。
4. 重新啟動後可回補尚未終結委託與當日成交；無法安全回補時，禁止該商品新單並要求人工對帳。
5. 策略層合計淨部位必須能與券商帳戶層淨部位對帳；差異不可被隱藏。

## 名詞與不變量

### 策略訂單身分

每個策略訂單在送券商前都必須具備並持久化以下欄位：

- `StrategyInstanceId`：唯一策略實例。
- `RunGeneration`：同一實例重建後的執行世代，避免舊回報誤送至新執行器。
- `ClientOrderId`：策略端唯一委託識別碼。
- `OrderRole`：例如 `EntryLong`、`EntryShort`、`TakeProfit`、`StopLoss`、`Flatten`。
- `CycleId`：策略週期或交易回合識別碼；無週期策略可為空。
- `BrokerOrderId`、券商委託序號及原始請求序號：券商可回傳的識別碼。
- 商品、方向、價格、數量、策略意圖、累積成交量、終結狀態與最後回報水位。

映射以 `StrategyInstanceId + RunGeneration + ClientOrderId` 為策略側唯一鍵，並以所有可取得的券商識別碼建立反向索引。任何一筆券商回報只能解析為一筆持久化策略訂單或「隔離回報」，不得有第二種猜測路徑。

### 兩層部位與損益

策略帳本以 `StrategyInstanceId + Symbol` 為鍵，依該策略自己的成交計算部位、成交均價、已實現／未實現損益及費用。帳戶帳本以帳戶與商品為鍵，只處理券商實際淨部位、可用風險與對帳。

同商品的策略多空對沖時，策略帳本可以同時保有多頭與空頭策略部位；帳戶帳本可能為淨額零。此差異是允許的，只要所有策略虛擬淨部位加總等於券商帳戶淨部位。

券商 `PositionEffect` 是帳戶層送單語意，並非策略歸屬來源。策略的「平倉」代表減少該策略帳本部位；中央執行層根據帳戶層狀態決定送出 Open、Close 或 Auto，回報仍固定路由至原策略訂單。

## 元件設計

### StrategyOrderRouteStore

新增共用、可持久化的策略訂單路由存放區。它負責原子寫入訂單意圖、識別碼映射、回報水位與回補狀態，並提供：

- 以策略側唯一鍵註冊送單前意圖；
- 以券商識別碼補齊或查詢路由；
- 以成交識別碼或累積成交量水位去重；
- 列出未終結訂單與隔離回報；
- 保存策略執行個體、參數快照、商品、帳戶及世代資訊。

初版可使用現有本機訂單儲存的相同可靠持久化機制，但其資料模型必須獨立表達策略欄位，不能只從字串格式的 `OrderId` 反推。寫入失敗時不得送券商。

### StrategyExecutionRouter

由 `LiveStrategyService` 擁有一個中央路由器。每個 `KgiLiveStrategyExecutionService` 在提交、取消、成交與生命週期變化時都透過它登錄與解析。路由器職責：

- 為策略訂單配置／保留唯一 `ClientOrderId`；
- 先登錄送單意圖，再允許券商呼叫；
- 在券商確認後更新券商識別碼；
- 將券商回報精確派送至所屬執行器；
- 對未知或歧義回報建立隔離紀錄並通知商品風控；
- 對重複、晚到或亂序回報使用水位去重，維持單調的成交與生命週期。

`KgiLiveStrategyExecutionService` 保留單一策略的訂單條件、風控與策略回呼，但不得自行以商品或帳戶持倉尋找回報歸屬。

### AccountReconciliationCoordinator

帳戶層對帳協調器在啟動、重啟回補及重要券商回報後執行：

1. 彙總策略帳本的每商品淨部位。
2. 讀取券商實際帳戶淨部位與未完成委託。
3. 比對淨部位、已知委託與成交水位。
4. 一致時標示商品可交易；不一致、未知券商委託或無法歸屬成交時標示商品為 `Quarantined`。

`Quarantined` 商品不可新增策略委託，但仍允許查詢、撤單、人工核對及經明確授權的風控平倉。隔離狀態與原因需顯示在實盤策略中心。

## 實盤資料流

### 新委託

1. 策略透過既有 `PaperOrderRequest` 發出意圖。
2. 執行器向中央路由器保留策略側唯一鍵並寫入 `Prepared` 記錄。
3. 路由記錄安全持久化後，執行器才呼叫券商。
4. 券商接受／回報後，更新券商識別碼與訂單狀態。
5. 成交或生命週期回報依映射送回唯一策略，並更新策略帳本。

若步驟 2 或 3 失敗，禁止送券商。若步驟 4 的網路結果不確定，訂單留在 `SubmissionUnknown`，重啟或人工對帳時以券商查詢解析，禁止重送相同策略意圖。

### 成交、撤單與平倉

策略的取消與關閉請求只使用自己的 `StrategyInstanceId` 查詢路由。中央路由器僅取消屬於該實例的券商訂單。策略平倉成交更新該策略帳本；即使帳戶層因其他策略反向部位而需以 Open 或 Auto 送券商，策略端仍保留 `Flatten`／`TakeProfit`／`StopLoss` 的原始角色與自己的損益。

## 重啟回補

### 重啟前持久化

每次策略啟動與每個訂單狀態變化都保存策略定義、參數快照、帳戶、商品、世代、映射、成交水位與策略帳本檢查點。持久化資料必須足以在沒有原記憶體物件的情況下重建路由。

### 回補程序

1. 啟動時載入所有未完成策略執行個體與路由紀錄；所有實例先進入 `Recovering`／暫停狀態，禁止新訊號及新單。
2. 以原帳戶及商品向券商取得未完成委託、當日成交及實際淨部位。
3. 先以 `BrokerOrderId`、券商序號與原始請求序號比對；不足時才以已持久化的精確條件交叉驗證，仍不可用商品或時間單獨推測。
4. 將可唯一解析的成交、取消與拒單套用回原策略。成交以成交識別碼優先，否則以累積成交量單調水位去重。
5. 重建策略帳本並與帳戶帳本對帳。
6. 無差異且所有路由完整時，實例維持 `Suspended`，由使用者明確按「繼續」後才恢復訊號。
7. 有未知券商委託、未知成交、重複／回退的成交量、帳戶淨部位差異或路由衝突時，商品標示 `Quarantined`；不得自動啟動或自動猜測分配。

### 冪等與晚到回報

每筆成交使用券商成交識別碼、或以 `BrokerOrderId + 累積成交量 + 回報序號` 建立去重鍵。已處理回報不可再次改變策略帳本。已終結訂單仍保留映射至晚到回報觀察期結束；觀察期前不可刪除。

## UI 與可觀測性

實盤策略中心的每個策略頁籤與管理表格增加或揭露：策略實例、執行世代、回補狀態、路由完整性、策略部位、帳戶商品淨部位、對帳差異、未完成策略訂單數、隔離原因、最後成功回補時間。

每筆成交紀錄顯示策略實例、策略角色、ClientOrderId、BrokerOrderId、券商委託序號、成交識別碼、價格、數量、費用及是否為回補事件。手動單固定標記 `Manual`，不可併入策略績效。

## 錯誤處理與風控

- 路由持久化失敗：拒絕新單，顯示明確原因。
- 送單結果不確定：保留 `SubmissionUnknown`，禁止同意圖重送，要求券商查詢。
- 未知回報或對帳不一致：商品隔離，禁止新單。
- 策略關閉：只處理該策略的未完成委託與策略虛擬部位；其他策略持續運作。
- 程式重啟：預設不自動恢復策略；回補成功後仍等待使用者恢復。

## 測試與驗收

新增測試須先失敗，再以最小實作通過。至少涵蓋：

1. 相同 225MC、不同策略實例的反向成交，回報各自路由、部位與損益正確。
2. 關閉策略 A 不取消策略 B 的委託、不改變策略 B 的帳本。
3. 同一券商成交回報重送時，策略損益只計一次。
4. 回報亂序或晚到時，仍保有原策略角色與正確累積成交量。
5. 重啟後可回補已知未完成委託與停機期間成交，且不自動恢復策略。
6. 未知券商委託、未知成交或帳戶／策略淨部位差異會隔離商品並阻擋新單。
7. 手動單不會被分配到任何策略帳本。

完整驗收需包含既有策略框架、實盤執行、訂單管理與週期掛單的冒煙測試，以及 Debug／Release 建置。沒有券商沙盒或正式回報證據時，只能宣稱測試替身驗證，不得宣稱已驗證正式券商行為。

## 非目標

- 不修改 MR、MODWT、PQC 或其他策略的訊號與參數。
- 不允許重啟後自動恢復送單。
- 不以策略帳本取代券商正式帳務或帳戶層風控。
- 不為了匹配帳戶淨部位而把未知券商委託或成交任意分配給策略。
