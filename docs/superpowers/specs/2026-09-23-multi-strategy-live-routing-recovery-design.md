# 多策略實盤委託歸屬、虛擬分帳與重啟回補設計

日期：2026-09-23

## 1. 目標

允許多個策略實例同時交易相同商品，包含方向相反的策略；所有委託、狀態回報、成交、撤單、拒單、晚到成交與重啟回補，都必須精確回到原始策略實例。策略部位與績效使用策略虛擬分帳，券商帳戶淨部位只負責帳戶對帳、實際風控及送單的開平倉語意。

本設計禁止以商品、帳戶淨部位、成交抵達順序或「目前只有一個策略」等推論決定策略歸屬。無法唯一對應的事件一律隔離，不能寫入任何策略帳本。

## 2. 範圍

本次架構涵蓋：

- 實盤策略委託的中央歸屬路由；
- 每個策略實例的獨立虛擬部位與績效帳本；
- 帳戶商品層的淨部位、人工單與整體風控帳本；
- 委託映射、成交去重水位與策略復原狀態的持久化；
- 程式重啟及斷線重連後的委託、成交、部位回補；
- 無法歸屬、歸屬衝突及帳務不一致的隔離流程；
- 策略中心的回補、暫停、隔離與人工對帳狀態；
- 模擬與實盤共用的策略分帳語意，以及實盤專屬的券商路由與回補。

本次不修改 MR、PQC 或其他策略的交易參數，也不在測試中送出真實委託。

### 2.1 適用策略與一致性要求

本架構不是 PQC 專用功能，必須一次套用到目前已註冊的全部六種策略：

- `MeanReversionScalper`
- `WaveletScalper`
- `NikkeiMicrostructureAlpha`
- `MiniLeadMicro`
- `OrderBookTrend`
- `PeriodicQueueCycle`

上述六種策略以及未來新增策略，都必須走相同的 `StrategyHost → StrategyInstanceRunner → 中央實盤委託路由器 → OrderManager` 管線，使用相同的 ownership、策略帳本、帳戶帳本、成交去重、隔離與重啟回補規則。每個實例可以保留同型別的輕量 facade，但 facade 不得直接訂閱券商事件、持有獨立 ownership 儲存或另算損益；不得為某一策略建立不同的券商路徑或回補捷徑。

目前六種策略都已使用共用主機與策略帳本，但只有 `PeriodicQueueCycle` 已實作 `IManagedOrderStrategy` 並自行提供 `ClientOrderId`、`CycleId` 與 generation。其餘五種策略仍使用整批 `CancelAllRequested`，且委託未提供完整 managed identity；因此現況只算部分符合，實作計畫必須將六種策略全部遷移完成，不能只修改 PQC 或中央服務後宣稱完成。

遷移完成後，每種策略都必須：

- 實作共用的 managed-order 生命週期契約，接收屬於自己的接受、部分成交、成交、撤單中、撤單完成、撤單失敗與拒單；
- 每筆委託在離開策略前具備非空且穩定的 `ClientOrderId`、`CycleId`、strategy generation、`PaperOrderRole` 與 `StrategyInstanceId`；
- 只以精確 `ClientOrderId` 撤銷特定委託；`CancelAll` 僅能表示「取消本策略 ownership 下的全部委託」，不能擴大到同商品其他策略；
- 實作版本化策略復原 checkpoint，保存該策略安全恢復所需的最小狀態；
- 從 `IStrategyPerformanceView.GetPosition(StrategyInstanceId, Symbol)` 讀取自己的虛擬部位，不得讀取帳戶淨部位作為策略持倉；
- 在模擬、重播與實盤使用同一組策略委託識別與生命週期語意，只有底層執行轉接不同。
- 實盤一律通過同一組登入、帳號、商品白名單、單筆一口、每日虧損、持久化及隔離檢查；策略不能繞過中央驗證。

`LiveStrategyService` 註冊工廠時必須驗證這些能力；缺少 managed-order 或 recovery 能力的策略可以保留模擬／重播，但不得啟動實盤。

## 3. 核心不變條件

1. `StrategyInstanceId` 在存續及回補期間唯一；重建同一實例時沿用原 ID，重新開始的新一代使用遞增的 `StrategyGeneration`。
2. `ClientOrderId` 在同一 `StrategyInstanceId + StrategyGeneration` 內唯一，不得重用。
3. 策略委託的核心歸屬欄位一旦寫入便不可變：`StrategyInstanceId`、`StrategyGeneration`、`ClientOrderId`、`Symbol`、`OrderRole`、`CycleId`。
4. 券商回報只能經由已持久化的券商識別別名解析至唯一的核心歸屬；零筆或多筆候選都必須隔離。
5. 成交只有在歸屬唯一且尚未處理時，才能同時寫入原策略帳本與帳戶帳本。
6. 同商品不同策略的多空部位不得互相覆寫或沖銷；沖銷只存在於帳戶彙總視圖。
7. 關閉、撤單及風控平倉以 `StrategyInstanceId` 為邊界；除帳戶級緊急風控外，不得操作其他策略的委託或虛擬部位。
8. 回補完成後所有恢復的策略維持暫停；只有使用者明確按下「繼續」，且商品未隔離、復原狀態版本相容、帳務對帳通過時才可恢復訊號。

## 4. 架構

### 4.1 中央實盤委託路由器

新增帳號範圍的中央路由器，生命週期隸屬 `LiveStrategyService`，而不是隸屬個別策略執行器。現有每策略 `KgiLiveStrategyExecutionService` 保留為策略端 facade，但送單、撤單、券商回報訂閱、回補及隔離由中央路由器統一處理。

中央路由器維護三種索引：

- 策略索引：`StrategyInstanceId + StrategyGeneration + ClientOrderId`；
- 本機委託索引：`OrderId`；
- 券商別名索引：帳號、交易日及券商可提供的 `ExternalOrderId`、`OrgCnt`、`Cnt`、`OrdNo`、`RequestId`。每個別名只能指向一筆策略歸屬。

券商 ID 可能在送單後才取得，因此映射分兩階段建立：

1. 送券商前先寫入 `SubmitPending` 的不可變策略歸屬與本機冪等鍵；持久化成功後才允許呼叫券商 API。
2. 券商接受或回報到達後，將其識別碼作為別名追加至同一歸屬紀錄。增加別名不得修改策略核心歸屬。

若券商回報只帶部分識別碼，路由器可使用該識別碼查詢已持久化的唯一映射；不得以商品、價格、數量或時間相近作為後備匹配。若券商 API 無法回傳或回補任何可連到送單前冪等鍵的識別碼，該事件進入隔離清單。

### 4.2 持久化模型

新增 append-only JSONL journal，沿用專案現有 JSON 生態且不新增資料庫相依。journal 每筆包含 schema version、單調遞增 revision、寫入時間、帳號、交易日、不可變策略歸屬、券商別名、生命週期狀態、累積成交量、已處理成交鍵及策略復原 checkpoint 版本。

關鍵寫入使用 write-ahead 規則：

- `SubmitPending` 必須在券商呼叫前寫入並完成 `Flush(true)`；寫入失敗時禁止送單。
- 券商 ID 綁定、撤單請求、生命週期終態、成交水位及策略 checkpoint 均以新 revision 追加，不覆寫舊紀錄。
- 定期將 journal 壓縮成 snapshot；snapshot 寫入暫存檔、flush 後以原子替換發布，原 journal 保留至 snapshot 驗證成功。
- 啟動時若最後一筆 JSONL 不完整，只捨棄該不完整尾端並記錄診斷；中段損壞、revision 倒退、重複歸屬或 schema 不相容會使相關商品進入隔離。

持久化紀錄至少保存至交易日結束後的設定保留期；仍有未完成委託、虛擬部位、待回補成交或隔離事件時不得清除。

### 4.3 成交冪等與亂序處理

成交優先使用 `BrokerOrderIdentity + ExecId` 作為唯一成交鍵。若券商沒有可靠 `ExecId`，使用該券商委託的單調累積成交量水位：只將新水位與已處理水位的正差額入帳。

- 即時回報與重啟回補重疊時，同一成交只入帳一次。
- 晚到成交即使發生於撤單確認之後，仍由 tombstone 映射送回原策略。
- 累積成交量下降、超過原委託量、相同成交鍵內容衝突或同一券商別名對應多筆策略歸屬時，停止該商品新單並隔離。
- 改單與撤單使用原訂單的 immutable ownership；新的券商操作序號只新增為別名，不建立新的策略歸屬。

## 5. 兩層帳本

### 5.1 策略虛擬帳本

現有 `PaperPortfolioLedger` 的權威鍵保持為 `StrategyInstanceId + Symbol`，並補入 `StrategyGeneration` 與成交冪等鍵。每筆已歸屬成交只更新原策略的：

- 虛擬淨口數與平均成本；
- 已實現、未實現損益；
- 手續費與完整交易統計；
- 進出場角色、週期及持有期間。

策略 A 做多、策略 B 做空同一商品時，A 與 B 各自保持非零部位；帳戶商品層即使為零，也不得將兩個策略標記為平倉。

### 5.2 帳戶商品帳本

新增帳號與商品範圍的彙總帳本，保存：

- 所有策略虛擬部位加總；
- 已辨識人工／外部訂單的獨立 `ManualExternal` 部位；
- 券商回報的實際淨部位、未完成委託與費用；
- 依相同市場標記計算的總經濟損益；
- 對帳差異與隔離原因。

人工單不寫入任何策略績效，但必須進入 `ManualExternal` 桶，讓下式可對帳：

```text
ExpectedAccountNet = Sum(StrategyVirtualNet) + ManualExternalNet
PositionDifference = BrokerAccountNet - ExpectedAccountNet
```

因券商使用淨額帳務，策略已實現損益與券商已實現損益的認列時點可能不同。對帳要求為同一標記價格下的「已實現 + 未實現 - 費用」總經濟損益一致，不要求兩層的已實現欄位逐時相等。

### 5.3 開平倉語意

策略只表達「增加／減少自己的虛擬部位」及 `OrderRole`。中央路由器在送券商前，根據帳戶商品帳本、商品規則及券商能力決定實際 `PositionEffect` 為 `Open`、`Close` 或 `Auto`。

券商回報的 `PositionEffect` 可用於帳戶對帳，但不得反向改變策略歸屬。例如帳戶淨部位為零時，策略 A 關閉虛擬多單所送出的賣單，可能在券商帳戶形成空單；這不影響它仍是策略 A 的虛擬平倉成交。

## 6. 重啟與斷線回補

### 6.1 啟動狀態

程式啟動後，`LiveStrategyService` 先進入 `Recovering`。此狀態允許查詢、接收券商回報、必要撤單與已授權風控平倉，但禁止所有策略新訊號與一般新單。

依持久化資料重建：

- 策略定義、實例 ID、generation、參數及商品；
- 委託歸屬、券商別名、生命週期與成交水位；
- 策略虛擬帳本與帳戶商品帳本；
- 策略專屬復原 checkpoint。

每個可實盤策略必須實作版本化復原契約，匯出及還原仍會影響安全行為的狀態，例如工作委託、週期、固定停損、單邊成交時間、冷卻時間及暫停／關閉狀態。checkpoint schema 不相容或缺少必要欄位時，不得繼續該策略；保留中央撤單及平倉能力並進入人工處理。

### 6.2 券商資料回補順序

1. 載入並驗證本機 snapshot 與 journal。
2. 建立所有路由索引，但保持策略 `Recovering`。
3. 向券商取得當日未完成委託、當日成交及帳戶商品淨部位。
4. 先綁定／驗證委託，再以成交鍵或累積水位回補成交，最後套用終態。
5. 還原每個策略 checkpoint，將已歸屬的缺漏生命週期與成交送回原策略。
6. 比對策略虛擬帳本、人工外部桶及券商帳戶帳本。
7. 通過者轉為 `RecoveredPaused`；失敗商品轉為 `Quarantined`。

即時回報可能與步驟 3 至 5 同時發生。中央路由器在單一序列化事件管線內處理即時與回補事件，並以同一成交冪等規則去重，不能建立兩套入帳路徑。

### 6.3 恢復交易

重啟後不自動啟動策略。使用者按「繼續」時必須再次驗證：

- 策略復原 checkpoint 版本相容；
- 該策略沒有未歸屬或衝突事件；
- 該商品帳戶部位及委託對帳差異為零；
- 商品未被帳戶級風控封鎖；
- 登入、商品白名單、單日損失與原有實盤確認仍通過。

任何條件不成立時，維持暫停並顯示穩定原因代碼。

## 7. 隔離與人工對帳

以下任一情況使相關商品進入 `Quarantined`，並停止該商品所有策略的一般新單：

- 券商事件沒有唯一策略映射；
- 同一券商別名出現多個策略歸屬；
- 成交鍵衝突或成交水位不可能；
- 策略虛擬部位加人工外部部位與券商淨部位不一致；
- 持久化資料損壞、版本不相容或策略 checkpoint 無法還原。

隔離期間仍允許：唯讀查詢、匯出對帳資料、依精確映射撤銷既有委託，以及經使用者明確授權的帳戶級風控平倉。隔離事件不能被自動分配至「最可能」策略。

解除隔離必須由使用者完成券商委託、成交與部位核對，再提交具稽核紀錄的修正映射或 `ManualExternal` 歸屬。系統重新計算兩層帳本並通過全部不變條件後，才可解除商品封鎖；解除後策略仍維持暫停，需逐一按「繼續」。

## 8. 策略關閉與帳戶風控

- 關閉策略 A 只選取 ownership 為 A 的本機條件與券商委託，並只將 A 的虛擬部位歸零。
- 策略 A 的撤單失敗、拒單與晚到成交只回到 A；策略 B 不因同商品而改變狀態。
- 策略平倉量來自 A 的策略虛擬帳本，不來自券商帳戶淨部位。
- 帳戶級緊急風控可以封鎖同商品所有策略，但每筆後續成交仍依原 ownership 分帳；不能為了快速歸零而抹除策略歸屬。
- 應用程式只有在所有策略委託、隔離 tombstone、人工外部風險及券商帳戶部位都安全時才允許退出。

## 9. 可觀測性與 UI

實盤策略中心增加：

- 每個策略的 generation、回補狀態、虛擬部位及回補原因；
- 每筆委託的 `StrategyInstanceId`、`ClientOrderId`、`BrokerOrderId`、角色、週期及歸屬狀態；
- 商品對帳表：券商淨部位、策略虛擬部位合計、人工外部部位、差異、未完成委託差異；
- 隔離清單：原始券商識別、事件類型、時間、原因代碼及人工處理狀態；
- `Recovering`、`RecoveredPaused`、`Quarantined`、`ReconciliationRequired` 等穩定原因代碼與繁體中文說明。

共用 `order-lifecycle.jsonl` 與 `executions.csv` 保留策略歸屬和券商識別；新增 recovery/reconciliation 診斷時沿用共用紀錄器，不建立策略專屬記錄器。紀錄不得包含登入密碼、API 密鑰或其他憑證。

## 10. 錯誤處理

- write-ahead 持久化失敗：拒絕送單，策略進入可恢復暫停。
- 券商送單結果不明：保留 `SubmitPending`，商品停止新單，等待券商查詢回補，不可直接重送。
- 回報未知或歸屬衝突：事件隔離，商品停止新單。
- 撤單失敗：保留原 ownership 與工作狀態，回送原策略並允許精確重試。
- checkpoint 寫入失敗：停止該策略新訊號；既有委託仍由中央 ownership 路由保護。
- 帳戶對帳差異：封鎖商品新單，不能以帳戶淨額覆寫策略帳本。

所有錯誤都必須保留原始事件、穩定原因代碼與可操作說明；可恢復問題不得誤標為不可逆的策略程式錯誤。

## 11. 驗收測試

### 11.1 多策略與分帳

- 同時啟動兩個 225MC 策略，同商品同方向及反方向委託都可並行。
- 策略 A 多一口、策略 B 空一口後，兩個策略各自部位非零，帳戶淨部位為零。
- 策略 A 平倉、停損或撤單不改變策略 B 的委託、部位、成本及損益。
- 策略績效使用各自實際成交及費用；帳戶總經濟損益與策略加人工外部桶可對帳。
- 對六個已註冊 factory 執行參數化測試，確認每一種策略皆走相同中央路由、策略分帳與精確取消契約。

### 11.2 精確路由

- 相同商品、相同價格、相同數量且回報亂序時，仍依券商別名回到正確策略。
- 撤單後晚到成交、撤單失敗、改單新序號、拒單及重複回報均回到原策略且只處理一次。
- `ClientOrderId` 跨策略相同時以策略 composite key 隔離；同一策略 generation 內重複則拒絕。
- 未知或歧義券商事件進入隔離，任何策略帳本都不變。

### 11.3 重啟與 crash window

- 在 write-ahead 前失敗時沒有券商送單；write-ahead 後、券商呼叫前中斷時不會自動重送。
- 券商已接受但本機尚未綁定 BrokerOrderId 時中斷，重啟可透過冪等鍵／券商別名恢復唯一映射；無法唯一恢復則隔離。
- 即時成交與回補成交重疊時，以 `ExecId` 或累積成交水位去重。
- journal 不完整尾端可安全復原；中段損壞與 schema 不相容會封鎖而非猜測。
- 回補完成且對帳一致後狀態為 `RecoveredPaused`，不會自動送單；使用者明確繼續後才恢復。
- 回補時仍有虛擬部位與工作委託，策略 checkpoint 可還原保護狀態與原委託 ownership。

### 11.4 人工單與對帳

- 已辨識人工單只更新 `ManualExternal`，不進入任何策略績效。
- 策略虛擬部位加人工外部部位等於券商淨部位時通過對帳。
- 不相等時封鎖該商品新單，UI 顯示差異與隔離原因。
- 只有完成具稽核紀錄的人工修正並重新對帳後才能解除隔離。

### 11.5 回歸與安全

- 模擬／重播仍以 `StrategyInstanceId + Symbol` 獨立分帳，不依賴券商路由器。
- 既有 MR、Wavelet、Nikkei Alpha、Mini Lead、Order Book Trend、PQC 的生命週期與關閉測試持續通過。
- 六種策略建立的每筆委託都有完整 ownership 欄位；任一 factory 缺少 managed-order 或 recovery 能力時，實盤註冊測試必須失敗並指出策略類型。
- 六種策略各自接受只屬於自己的亂序生命週期與成交；同商品另一策略的事件不得改變其狀態或帳本。
- OrderManagement、StrategyFramework、各策略 smoke tests 與 Release 建置通過。
- 所有測試使用 fake gateway；不得為驗證送出真實券商委託。

## 12. 移轉與相容性

現有尚未持久化 ownership 的活動實盤委託不能自動升級為策略委託。首次啟用新架構時：

1. 若券商帳戶沒有未完成委託且帳戶部位為零，可建立空白新 journal。
2. 若存在委託或部位，先進入隔離，由使用者標記為 `ManualExternal` 或提供可驗證的策略映射。
3. 未完成移轉前禁止策略新單。

既有模擬紀錄與策略參數格式保持可讀；新的 generation、ownership、recovery 欄位採版本化擴充。舊資料缺少欄位時明確標示 unavailable，不得補造策略歸屬。

## 13. 完成定義

完成不等於單元測試能建置。必須同時滿足：中央路由只有唯一映射才交付事件、兩層帳本不變條件成立、重啟回補具冪等性、隔離不會污染策略績效、同商品反向策略可獨立關閉，以及所有恢復策略維持暫停直到使用者明確繼續。實盤券商連線與真實回報仍需另行授權，在受控時段驗證後才能聲稱通過實盤驗收。
